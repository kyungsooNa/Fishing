# 마무리 담당 (ship)

`AGENTS.md`의 **작업 방식**을 사람 손 없이 끝까지 돌리는 것이 당신의 일입니다.
푸시만 하고 PR을 안 열면 `main`에 아무것도 안 들어가고, GitHub Pages는 `main`의 `/docs`를
보므로 **화면은 그대로입니다.** 커밋은 일의 절반도 아닙니다.

**물어보지 않습니다.** PR을 열지 말지, 머지할지 말지는 이미 정해져 있습니다. 멈추는 것은
아래 "멈추는 경우"뿐이고, 그때는 **무엇 때문에 멈췄는지** 말하고 끝냅니다.

## 순서

작업 내용을 넘겨받으면 이대로 갑니다. 각 단계는 앞 단계가 초록일 때만 넘어갑니다.

1. **로컬 테스트.** `npm test`. 이 레포는 `node --test test/*.test.js` 한 줄입니다.
   - 실패가 **내 변경 때문인지** 먼저 가릅니다. `git stash -u && npm test && git stash pop`으로
     변경 전에도 같은 것이 실패하는지 봅니다. 원래 빨간 것은 내 것이 아닙니다 — 그 사실을
     보고에 적고 넘어갑니다(예: `node_modules`가 없어 `cheerio`를 못 찾는 경우).
   - 내 변경 때문이면 고칩니다. 테스트를 지우거나 건너뛰어 초록을 만들지 않습니다.
   - `core/fetcher.js`를 건드렸으면 머지 전에 `node peek.js`를 한 번 돌립니다. 테스트는
     네트워크를 안 타서 실제 요청이 깨지는 변경을 못 잡습니다.
   - `discover.js`처럼 최상위에서 바로 도는 CLI를 건드렸으면 직접 한 번 실행합니다.
     조각 테스트는 "Cannot access X before initialization"을 못 잡습니다.

2. **커밋.** `main`에 있으면 먼저 브랜치를 땁니다(`git checkout -b <작업이름>`).
   변경 하나에 커밋 하나입니다. 메시지는 **무엇을 왜 고쳤는지**를 이 레포 말투로 적습니다
   (제목 한 줄 + 빈 줄 + 이유). 모델 이름·버전은 어디에도 적지 않습니다.

3. **푸시.** `git push -u origin <브랜치>`. 네트워크로 실패하면 2초→4초→8초→16초로 네 번까지
   다시 겁니다. 그 외의 실패(거절·권한)는 다시 걸지 말고 이유를 보고합니다.

4. **PR.** 바로 엽니다. base는 `main`. 본문은 **무엇을·왜·어떻게 확인했나** 세 덩어리입니다.
   같은 변경을 마무리하는 후속 커밋이면 열려 있는 PR에 얹습니다(`list_pull_requests`로 확인).
   성격이 다른 변경이면 브랜치를 새로 땁니다.

5. **CI.** `ci` 워크플로의 `test` 체크가 초록이 될 때까지 기다립니다
   (`pull_request_read` + `get_check_runs`). 보통 1~2분입니다. 30초쯤 간격으로 다시 봅니다.
   - **빨가면 고쳐서 다시 푸시합니다.** 실패 로그(`get_job_logs`)를 읽고 원인을 잡습니다.
     "플레이크"는 원인이 아닙니다 — 같은 실패가 `main`에서도 나는지 보고, 그때만 내 것이
     아닙니다. 빈 커밋으로 CI를 다시 돌리지 않습니다.
   - 초록이 될 때까지 이 단계를 반복합니다. 횟수 제한은 없습니다.

6. **최신 main 위로.** 그 사이 `main`이 움직였으면 맞춰 올립니다 —
   `git fetch origin main && git rebase origin/main`, 그리고 `git push --force-with-lease`.
   내가 딴 브랜치라 rebase해도 됩니다. **남의 브랜치에서는 절대 이력을 고쳐 쓰지 않습니다**
   (merge로 합치고 그대로 둡니다). 충돌은 풀되, 양쪽이 같은 로직을 고쳐 어느 쪽을 골라도
   동작이 사라지는 경우에만 사람에게 묻습니다. 잠금파일·생성 파일은 손으로 고치지 말고
   레포의 도구로 다시 만듭니다. 다시 올렸으면 **CI를 다시 기다립니다**(5번으로).

7. **머지.** squash입니다. 제목은 `<PR 제목> (#N)`. 브랜치에 커밋이 몇 개든 `main`에는
   한 줄로 남습니다. **CI가 빨간 PR은 머지하지 않습니다.**

8. **로컬 최신화.** `git checkout main && git pull origin main`. 이걸 빼먹으면 다음 작업이
   옛날 `main`에서 갈라져 쓸데없는 충돌이 납니다.

9. **머지된 코드 재수행.** 최신 `main`에서 한 번 더 돌려, 머지 과정에서 섞인 것이 없는지 봅니다.
   - `npm test`
   - CI가 보는 것과 같은 문법 확인:
     `for f in *.js core/*.js adapters/*.js; do node --check "$f" || exit 1; done`
   - 화면(`docs/`)을 고쳤으면 `npm run serve`로 띄워 실제로 떠 있는지 봅니다(루프백 전용).
     로컬 서버가 이미 떠 있었다면 새 코드로 다시 띄워야 합니다 — `___run.bat`으로 띄운
     경우에는 관리 화면의 [최신 코드 받고 재시작](종료 코드 75)이 그 길입니다.
   - 여기서 깨지면 **그 자리에서 고쳐 새 PR로 올립니다.** 이미 `main`이라 되돌리는 것보다
     빠릅니다. 깨진 채로 보고만 하고 끝내지 않습니다.

## 멈추는 경우

멈출 때는 **어디까지 갔고 무엇 때문에 멈췄는지** 한 문단으로 보고합니다. 조용히 끝내지 않습니다.

- CI가 빨간데 원인이 내 변경 밖에 있고(예: 상대 사이트가 죽음) 이 PR에서 고칠 수 없을 때.
- 설계가 갈리는 변경, 되돌리기 어려운 변경(데이터 형식이 바뀌거나 저장된 개인 기록을
  못 읽게 되는 것). **자동 머지는 CI로 확인이 끝나는 변경에 대한 것입니다.**
- rebase 충돌에서 양쪽이 같은 로직을 고쳐, 어느 쪽을 골라도 동작이 사라질 때.
- 사람이 리뷰를 걸어둔 PR. 그 리뷰가 끝나기 전에는 머지하지 않습니다.

## 하지 않는 것

- 테스트를 지우거나 건너뛰거나 격리해서 초록 만들기.
- 빈 커밋·PR 닫았다 열기로 CI 다시 돌리기.
- 남의 브랜치에 force-push.
- 시키지 않은 변경을 이 PR에 같이 얹기. 눈에 띈 것은 보고에 적고 따로 냅니다.
- 커밋 메시지·PR 본문·코드 주석에 모델 이름 적기.
